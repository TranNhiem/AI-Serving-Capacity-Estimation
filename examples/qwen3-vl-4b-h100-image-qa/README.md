# `qwen3-vl-4b-h100-image-qa` — one H100, one image corpus, and chapter 9 end to end

> *"How many concurrent visual-QA sessions can one H100 carry before its declared SLO breaks?"*

This example answers that question by measuring the full path rather than composing a forecast
from a previous campaign. It is the repository's first multimodal worked example, its first
bundle-backed example, and its first example whose numbers were measured by this project end
to end. It also closes the gap recorded by the historical changelog: a dense-model report on
the same H100 hardware.

The model is Qwen3-VL-4B-Instruct, served by vLLM on one H100 SXM with TP=1. The workload is
open-ended visual question answering over a FineVision QA split using the LLaVA/ShareGPT
record shape. Each request carries one image, sent base64-inline through the OpenAI-compatible
chat API. Output is capped at 512 tokens with real EOS, so answer length remains an outcome of
the corpus unless the cap truncates it.

| path | what it is |
|---|---|
| `bundle/records.jsonl` | generated by `ascep bench`, one request per line with its token and timing observations |
| `vllm_server.out` | the complete serving-engine log for the ladder |
| `bundle/environment.json` | the hardware, software and process state recorded while serving |

There is no builder script. The bundle is the measured artifact, not a file reconstructed from
parameters. Every summary number in this README must be recoverable from the bundle.

The Python, CUDA and package rows come from `bundle/environment.json`, which the harness
probes in its own process. That capture describes the benchmark client, and only coincides
with the server because this run put both on the same allocated GPU node; split the two
across hosts and those rows stop describing what served the requests. The capture says so
itself, in its own "packages_source" note.

The vision tower is declared as replicated per rank rather than sharded. At tensor-parallel
widths greater than 1, each rank still holds a full copy of the vision tower, so its per-GPU
weight bytes do not fall by the TP factor the way the language-model weights do, and the
weights floor inherits that replication. At TP=1 the distinction is numerically invisible —
there is only one rank — which is exactly why it must be declared from the deployment rather
than inferred from the model name.

## What was run

The benchmark drew from a 2,000-record corpus,
`finevision-open-ended-qa-split1.jsonl`, and issued 17,680 requests across the ladder — one
line each in `bundle/records.jsonl`. The workload's shape was fixed before the
ladder ran: one image per request; images base64-inline; output capped at 512 tokens;
concurrency rungs of 1, 2, 4, 8, 16, 32, 64 and 128; three 180-second repetitions at every
rung; closed-loop load, in which the stated concurrency is the number of request streams
sustained rather than a Poisson arrival rate.

The declarations split across layers, and the attribution matters. At the model layer,
`input_modalities` is ["text", "image", "video"] and `reasoning_modes` is ["non-thinking"];
these describe what the checkpoint accepts and how it answers, and they belong to the model
declaration rather than the serving one. Both are lists because both are capability sets: the
checkpoint accepting video is a property of the checkpoint, and says nothing about whether the
deployment below it will serve one. The serving declaration records what the deployment
delivered rather than what the workload intended: `mm_processor_cache_gb` is 0, image
transport is base64-inline, and the pixel budget is 16,777,216. The 512-token output cap is a
workload field (`max_output_tokens`), because it is a property of the requests sent, not of
the server that answered them — the same server would answer a different cap.

The `image_resolution_mix` declaration names the five most common image resolutions. That the
five are the head of a long tail rather than the corpus is not an apology, it is a fact the
bundle records: the histogram in `bundle/run_configs.json` holds 1,183 distinct resolutions,
and the five most common together cover 11.4% of requests — the declared five sum to 11.1%,
and are not quite the same five, because a declaration written from the corpus and a
histogram observed over issued requests sample the same long tail independently. Either way
the head is a ninth of the traffic. The declaration is a summary and says so. It does not
license the reader to treat
the distribution as five-point support, and a predictor configured only for those sizes does
not thereby measure the rest of the corpus.

Prefix caching was left **on** in the engine and defeated in the workload, which is a
deliberate combination rather than a contradiction. The engine declares `prefix_caching` on;
the workload declares its cache policy as unique-prefix, which prepends a distinct token to
every request, so no two requests in the run share a prefix and the cache has nothing to
return. The reason to do it this way is the rung ordering: the ladder climbs from 1 to 128, so
a shared prefix would let each rung answer partly out of a cache the rung below it filled, and
the error would run one way only — every higher rung would look faster than it is, and the
throughput ceiling would appear further away than it is. This is the same field that
[`moe-26b-h100-tp2`](../moe-26b-h100-tp2/) names as the single unmeasured assumption its
headline is most sensitive to. Here it is measured, and neutralized by construction, which is
what that example says it would have taken to close the gap.

Video is inapplicable, not unknown. The engine was configured with a per-prompt video limit of
0 and therefore refuses video outright; the video declarations are marked inapplicable on that
basis rather than left as unmeasured unknowns. No video capacity conclusion is drawn, and the
image run does not establish one.

GPU utilization and GPU memory utilization, by contrast, are genuinely unknown — and always
are in a report this harness emits. A load generator cannot see the GPU; that observation must
come from the serving host. The harness declares both unknown with that reason rather than
guessing at them. This is the protocol's rule applied to the harness itself: it must not
publish what it cannot observe, even where the number would be welcome.

## What chapter 9 is demonstrating

This example does not add a vision floor. It demonstrates where multimodal costs land in the
existing model. The vision tower is resident GPU memory and lands on the weights floor. The
image tokens it expands are prompt tokens and occupy KV for the session. The generated answer
tokens drive the throughput floor and enter averaged context like any other output. The
binding floor is still chosen from weights, KV and throughput.

Image tokens are context and are charged as context. The API reports one aggregate
"prompt_tokens" count containing both the text prefix and the expanded image representation,
and does not expose an image-token component separately. The run row's field is
`context_tokens`, computed as the mean of input tokens plus output tokens per request, taken
over only those requests that reported both counts. A half-reported request contributes
nothing: a mean over whichever records carried input counts added to a mean over whichever
records carried output counts could be a context no request ever had, yet it would sit in a
measured row as if it had been observed. The media expansion is already inside the server's
"prompt_tokens" count, and adding a media term again would double-count the image. The media
share of the prompt is not separately observable through this API, so the report declines to
split it rather than modelling it. A modelled split would read as a second measurement, and a
derived number in a measured table invites exactly the confidence the protocol exists to
refuse.

Reasoning accounting changes with mode, which is why the mode is a required declaration and
is declared `non-thinking` here. A thinking profile would change output length, decode time
and KV occupancy without announcing itself through the model name. TTFT in this report marks
the first visible content token; there is no thinking branch to separate that instant from a
first reasoning token, and no thinking-mode throughput is inferred from this run. The run has
one capacity profile and the declaration says which one it is.

Host-side decode and patchify are capacity inputs, not implementation detail, which is why
`mm_processor_cache_gb` is set to zero: every request pays decode and patchify, removing a
cache speedup that repeated benchmark media would otherwise expose and production traffic
might not receive. For the same reason the hardware layer declares `cpu_cores` as 12. The
machine has 112 cores; 12 is the scheduler grant available to the serving process, and a
capacity allocation is not machine inventory.

## The result

**Sustainable result:** 64 sustained request
streams at 2,564.8 output tokens per second.
The binding constraint is the declared SLO gates (`slo`).

| result | value | tier | binding constraint |
|---|---:|---|---|
| measured capacity | 128 concurrent streams at 2,668.1 output tok/s | measured | `slo` |
| sustainable capacity | 64 concurrent streams at 2,564.8 output tok/s | sustainable | `slo` |
| first SLO failure | 128, on the TTFT p95 gate (9.598 s measured against the 4 s bound) | — | — |

The two tiers are different numbers here, and that is the point of publishing both. Measured
is the engine ceiling with the gates ignored: 128 streams is where throughput stopped
climbing, and the engine reached it. Sustainable is the highest rung where every gate held
for every window: 64. Between them the server is still answering — it is answering too
slowly to promise. Sizing against 128 would sell a latency nobody measured; sizing against
64 leaves 4% of the throughput on the table and keeps the promise.

The SLO gates were fixed before the run: TTFT p95 no greater than 4 seconds, ITL p95 no
greater than 0.05 seconds, end-to-end p95 no greater than 60 seconds, and error rate no
greater than 1%. A rung passes only if all three repetitions satisfy every gate. One failing
window fails the rung, because capacity is defined by the worst served user, not by best-of-N
or majority vote.

| concurrency | mean `context_tokens` | output tok/s | TTFT p95 (s) | ITL p95 (s) | e2e p95 (s) | rung-level SLO outcome |
|---:|---:|---:|---:|---:|---:|---|
| 1 | 1,174.6 | 95.5 | 0.303 | 0.006 | 2.999 | pass |
| 2 | 1,137.6 | 189.3 | 0.306 | 0.006 | 3.213 | pass |
| 4 | 1,174.9 | 359.9 | 0.333 | 0.006 | 3.431 | pass |
| 8 | 1,225.6 | 669.6 | 0.416 | 0.007 | 3.784 | pass |
| 16 | 1,174.6 | 1,206.4 | 0.606 | 0.009 | 4.601 | pass |
| 32 | 1,181.4 | 1,922.4 | 1.131 | 0.013 | 6.333 | pass |
| 64 | 1,176.9 | 2,564.8 | 2.310 | 0.019 | 10.473 | pass |
| 128 | 1,160.2 | 2,668.1 | 9.598 | 0.025 | 19.349 | fail |

Each row publishes the median repetition at its rung, ranked by output tokens per second and
taking the lower median on a tie. The three repetitions are not pooled: averaging percentiles
across windows would publish a row no window ever exhibited, and the figures in one row must
be mutually consistent, so a single real repetition stands in for the rung. The row also
carries two flags that answer different questions — the median repetition's own pass flag,
and the rung-level outcome, which is what the final column reports. Because a rung fails on
its worst window, a passing median repetition can sit beside a failed rung-level outcome;
when it does, the row carries the grading sentence that produced the verdict, so the reader
is never left to re-derive it from the records. The raw per-request distributions, including
the 512-token truncation outcome, remain in `bundle/records.jsonl` and must agree with every
figure above.

## Why the report is partial

Recorded conformance grade: partial.

The checker returns three findings, all warnings, and no errors.

The reproducibility gap is the missing container digest (C8). The environment capture, the
engine log's non-default-args line (which carries the model path, `max_model_len`,
`max_num_seqs`, `mm_processor_cache_gb` and the per-prompt media limits), the framework
version and a sha256 manifest over every artifact are all present, but none of them
identifies the immutable runtime image that executed the serving process, and that omission
limits independent reconstruction of the run.

The other two (C6) record that the `theoretical` and `recommended` tiers are absent. Neither
is a defect in the measurement. The roofline belongs to `ascep size`, and this bundle came
from `ascep bench`, so the analytic path has not been run rather than lost. A `recommended`
tier derates a measurement by a headroom factor, and that factor is a policy choice; no
headroom policy has been declared for this deployment, so inventing one to fill the row would
publish a procurement number nobody chose.

**partial** is a legitimate state, not a concealed failure. It says the measurements are
present while some declared input is not. It does not mean the requests did not run, and it
does not make the result conforming. A `notes` entry cannot close the digest gap: a note can
explain a missing digest but cannot substitute for one.

Closing the digest gap requires recording it when the serving image is launched and rerunning the
serving and benchmark ladder, environment capture, manifest and conformance checks against the
resulting bundle. Writing the digest of a current image beside an old run would not prove
which image produced the old measurements.

## What not to conclude

- **Do not scale from one GPU.** TP=1 on one H100 does not measure sharding, replicated
  vision towers at TP greater than 1, interconnect cost or multi-replica scheduling.
- **Do not generalize from this corpus.** FineVision QA records in this record shape do not
  represent every VQA distribution, document workload or production image stream.
- **Do not treat five resolutions as the resolution distribution.** They are the declared
  head. The tail remains in the corpus and in the bundle.
- **Do not infer video capacity.** The server refused video by configuration.
- **Do not infer thinking-mode capacity.** This is a `non-thinking` run and says nothing
  about a thinking profile of the checkpoint.
- **Do not convert closed-loop concurrency into arrival-rate service.** No Poisson arrival
  process, burst profile or queueing margin was measured.
- **Do not quote a tier without its rung and floor.** Capacity moves with context length and
  concurrency, and the named binding constraint is part of the answer.
- **Do not assume these SLO gates are universal.** The thresholds were declared for this
  example.
- **Do not drop the output cap from the result.** The 512-token cap is part of the measured
  workload, and its truncation outcome must travel with every throughput figure.
- **Do not assume cached preprocessing in deployment.** The processor cache was deliberately
  disabled; enabling it changes host load for repeated media.
- **Do not treat a partial grade as either conforming or invalid.** It is a published
  measurement with a declared reproducibility gap.
